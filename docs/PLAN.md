# План разработки Fragmentor

Как работать с этим планом:

- Один шаг — одна сессия Claude Code. Запуск: `/step 1`, `/step 2` и так далее.
- После шага: проверяю результат, коммичу, делаю `/clear` и только потом беру следующий шаг.
- Статусы: `[ ]` не начат, `[~]` в работе, `[x]` готов. Обновляет их Claude в конце шага.
- В разделе «Что сделано» Claude коротко пишет итог шага: это память для следующих сессий.

---

## Шаг 0. Подготовка (вручную, без Claude)

- [ ] Перевыпустить токен бота в BotFather и положить новый в `bot/.env` (шаблон — `bot/.env.example`).
- [ ] Установить Go, Git и Claude Code, открыть эту папку в VS Code, сделать `git init` и первый коммит.
- [ ] Положить в `bot/.env` ключ FACEIT Data API (server-side ключ из приложения на developers.faceit.com).
- [ ] Скачать 2–3 свои свежие демки FACEIT (`.dem.zst`) в `bot/testdata/`.
- [ ] Для этих же матчей сохранить скриншоты статистики FACEIT и Scope.gg — понадобятся для сверки формул.

## Шаг 1. Каркас бота и /start [x]

Цель: бот запускается локально и отвечает на /start.

- Изучить README и примеры `go-telegram/bot`, конспект — в `docs/notes/go-telegram-bot.md`.
- Go-модуль в `bot/`, структура: `cmd/bot`, `internal/config`, `internal/telegram`,
  `internal/i18n`, `internal/storage`.
- Конфиг из переменных окружения (локально — `bot/.env`), логи через `slog`,
  корректное завершение по SIGINT/SIGTERM.
- SQLite с механизмом миграций и первой таблицей `users`
  (telegram_id, username, language, joined_waitlist_at, created_at).
- `/start`: приветствие и запись в лист ожидания беты, на русском или английском по `language_code`.
  Повторный `/start` не создаёт дубликат.
- `/help`: что умеет бот сейчас.
- При запуске бот регистрирует команды и описания через Bot API
  (setMyCommands, setMyDescription, setMyShortDescription) для `ru` и `en`.
- Makefile с целями `run`, `test`, `lint`, `build`. Короткий `bot/README.md` о запуске.

Готово, когда:
- бот локально отвечает на `/start` и `/help` на обоих языках;
- повторный `/start` не дублирует пользователя (есть тест);
- `go test ./...` проходит.

Что сделано (2026-10-29):
- Модуль `github.com/kolyxus/fragmentor/bot`, Go 1.27, go-telegram/bot v1.27.0, modernc.org/sqlite v1.61.0.
  Конспекты: `docs/notes/go-telegram-bot.md`, `docs/notes/modernc-sqlite.md`.
- `internal/config`: `TELEGRAM_BOT_TOKEN`, `DATABASE_PATH`, `LOG_LEVEL` из окружения и `.env`
  (свой парсер, окружение важнее файла).
- `internal/storage`: SQLite (WAL, `BEGIN IMMEDIATE`, `STRICT`, время в unix-секундах),
  миграции `migrations/NNNN_name.sql` + `schema_migrations`, таблица `users`, `JoinWaitlist`.
  Следующая миграция — `0002_...sql`.
- `internal/i18n`: все тексты на ru/en, язык по `language_code` (`ru*` → русский, иначе английский).
- `internal/telegram`: `/start` (очередь на бету, повторный — «ты уже в очереди»), `/help`,
  подсказка на прочие сообщения, только личные чаты; меню команд и описания регистрируются
  при старте, если отличаются; 4 воркера, корректная остановка по SIGINT/SIGTERM, recover.
- `cmd/bot`, `Makefile` (`run`, `test`, `lint`, `build`), `bot/README.md`.
- Проверено вживую на @fragmentor_ai_bot: ответы на ru и en, повторный `/start`, регистрация профиля.
  Telegram Desktop присылает `en` только при английских системе и интерфейсе — см. заметки.

## Шаг 2. Ранний деплой [x]

Цель: `/start` работает круглосуточно, лист ожидания копится уже сейчас.

- Сборка статического бинарника под Linux, systemd-сервис с автоперезапуском,
  `.env` и база на сервере вне папки с кодом.
- Пошаговая инструкция `bot/DEPLOY.md`: что копировать на сервер и какие команды выполнить.
- Перед деплоем проверить с сервера доступ к Telegram:
  `curl https://api.telegram.org/bot<TOKEN>/getMe`. Если ответ медленный или не приходит,
  остановиться и обсудить варианты (прокси или сервер за рубежом).

Готово, когда:
- бот работает на сервере и сам поднимается после перезагрузки;
- в `bot/DEPLOY.md` описано, как выкатить новую версию.

Нужно от тебя: доступ по SSH к серверу и выполнение команд из инструкции.

Что сделано (2026-10-30):
- `make build-linux` → статический `bin/fragmentor-linux-amd64` (`CGO_ENABLED=0`, `-trimpath -ldflags=-s`, ~11,8 МБ).
  Первая строка лога — `starting version=<коммит>[+dirty] dev_bot=...`, коммит из вшитой Go информации о сборке.
- `deploy/fragmentor.service`: пользователь `fragmentor`, бинарник `/opt/fragmentor/fragmentor`,
  секреты `/etc/fragmentor/fragmentor.env` (root, 600, читает systemd), база `/var/lib/fragmentor` (`StateDirectory`),
  `Restart=always`, песочница. Проверено в WSL Ubuntu 26.04 (systemd 259): `verify`, запуск, перезапуск после
  `kill -9`, остановка, `enable`, сеть и запись только в свою папку внутри песочницы, `systemd-analyze security` 1.4 OK.
  Из WSL нет выхода в интернет, поэтому бот против Telegram внутри песочницы не проверен.
- `bot/DEPLOY.md`: SSH-ключ и алиас `fragmentor-vps`, проверка Telegram скриптом `deploy/check-telegram.sh`,
  первая установка, выкатка новой версии с `.prev`, бэкап базы перед миграциями, откат, типовые ошибки.
- `TELEGRAM_DEV_BOT_TOKEN` важнее `TELEGRAM_BOT_TOKEN`, и тогда боевой токен не обязателен (тесты).
  Локально проверено: поднимается @fragmentor_dev_bot.
- `.gitattributes`: `*.sh` и `*.service` всегда с LF. `go mod tidy`.

Поправка (2026-11-02): сервер — не AdminVPS (там виртуальный хостинг сайта и почты), а VPS за рубежом
(Ubuntu 24.04, 1 ГБ RAM), где уже работает VPN: Xray в Docker на 443.
- В юните лимиты памяти: `GOMEMLIMIT=320MiB`, `MemoryHigh=380M`, `MemoryMax=400M`, `MemorySwapMax=128M`,
  `OOMScoreAdjust=1000` — при нехватке памяти убивают бота, а не VPN. Проверено в WSL временным юнитом:
  лимиты попадают в cgroup, `oom_score_adj` = 1000, процесс сверх лимита убивается и перезапускается.
- В DEPLOY.md: swap 2 ГБ и `vm.swappiness=10`, отключение входа по SSH по паролю после проверки ключа,
  проверка перед перезагрузкой, что контейнер Xray поднимется сам.
- SSH по ключу через алиас `fragmentor-vps` работает. Проверка Telegram с сервера (`deploy/check-telegram.sh`):
  соединение ~2 мс, запрос целиком ~40 мс, `getMe` с боевым токеном 77 мс — прокси не нужен.
- Установлено по DEPLOY.md 2026-11-02, бот работает на сервере с коммита `1225e48f341f`.
  После перезагрузки сервера бот поднялся сам: `active`, `dev_bot=false`, @fragmentor_ai_bot, `polling for updates`.
  Swap 2 ГБ и `vm.swappiness = 10` на месте, контейнер VPN `amnezia-xray` поднялся сам.
- Выкатка по разделу 4 прогнана на той же сборке: бэкап базы, `.prev`, замена бинарника, `restart`.
  Остановка корректная: `polling stopped` → `bot stopped` за миллисекунды, `Deactivated successfully`.

## Шаг 3. FACEIT Data API и привязка ника [x]

Цель: бот знает FACEIT-аккаунт пользователя и видит его матчи.

- Изучить документацию FACEIT Data API на docs.faceit.com: нужные эндпоинты, поля ответов, лимиты.
  Конспект — в `docs/notes/faceit-data-api.md`.
- Клиент Data API: игрок по нику, разбор ссылки на профиль, история матчей CS2,
  детали матча (карта, счёт, составы с уровнями и SteamID64, `demo_url`), статистика матча.
  Таймауты, ретраи, ограничение частоты запросов.
- Таблица `faceit_accounts` новой миграцией.
- `/link`: ник или ссылка → карточка «Это ты?» (ник, уровень, ELO) → кнопки «Да» и «Нет» → сохранение.
- `/matches`: последние 5 матчей (карта, счёт, дата, результат).
- Тесты на записанных ответах API через `httptest`.

Готово, когда:
- привязка и список матчей работают в боте;
- тесты клиента проходят без реальных запросов к FACEIT.

Что сделано (2026-11-03):
- Конспект `docs/notes/faceit-data-api.md`. Главное: лимит FACEIT — 20 запросов в секунду
  (по заголовкам `RateLimit-*`), поиск игрока по нику различает регистр, история без `from` отдаёт
  матчи любой давности, в истории нет карты, неверный ключ — 400 `invalid_token`.
- `internal/faceit` — свой клиент на `net/http`:
  - `PlayerByNickname` (при 404 — `/search/players` без учёта регистра), `Player`, `History`;
  - `Match` (карта, счёт, составы с уровнями и SteamID64, `demo_url`), `MatchStats` (K/D/A, HS, ADR,
    счёт таймов, остальное в `Raw`), `RecentMatches`;
  - `ParseNickname` и `ParseProfileLink` для ника и ссылки на профиль.
  - Попытка — 10 с, до 3 попыток при сетевых ошибках, 429 и 5xx; token bucket 5 запросов/с
    с запасом 10; ответ не больше 2 МиБ; в ошибках и логах нет URL, ников и ID.
- `cmd/faceitrecord` записывает ответы FACEIT в `internal/faceit/testdata/` и обезличивает их.
  Записаны: профиль, поиск, история 10 матчей, детали и статистика 5 матчей (среди них оба матча
  из `bot/testdata/`), ответы 404 и на неверный ключ.
- Миграция `0002_create_faceit_accounts.sql`; `LinkFaceitAccount`, `FaceitAccount`, `storage.ErrNotFound`.
- `/link`:
  - ник или ссылка → карточка «Это ты?»: ник, уровень, ELO и замечание, если заменяет другой аккаунт;
  - кнопки «Да, это я» / «Нет»;
  - без аргумента бот 10 минут ждёт ник следующим сообщением;
  - ссылку на профиль можно прислать и без команды.
- `/matches`: 5 последних завершённых матчей CS2 строками `31.10 20:03 · Cache · 16:19 · поражение`,
  время московское для ru и UTC для en.
- Middleware пропускает нажатия кнопок из личных чатов. Меню команд: start, link, matches, help.
  `FACEIT_API_KEY` обязательна.
- Проверено:
  - `gofmt`, `go vet`, `go test ./...` (и с `-race`);
  - временный тест против живого FACEIT, удалён: ник находится в любом регистре, 5 матчей
    с картами — за 0,4 с;
  - локальный старт dev-бота: `schema_version=2`, меню команд обновилось на обоих языках.
- Проверено вживую 2026-11-03 на @fragmentor_dev_bot (`make run`):
  - `/link` без ника, затем ник следующим сообщением → карточка → «Да»;
  - `/link` со ссылкой на профиль с заменой уже привязанного аккаунта;
  - `/matches` для двух разных аккаунтов, `/help`.
- Выкачено на сервер по разделу 4 `bot/DEPLOY.md` после коммита `79246cf`:
  на @fragmentor_ai_bot работают `/link` и `/matches`.

Доработка (2026-11-03), шаг снова в работе:
- Карточка «Это ты?» в `/link` — фото с аватаром игрока из Data API, текст карточки — подписью,
  кнопки те же; после «Да» и «Нет» меняется подпись. Нет аватара или фото не отправилось —

## Шаг 4. Парсер на реальных демках [x]

Цель: убедиться, что парсим демки FACEIT правильно.

- Изучить demoinfocs-golang: README, папку `examples`, пакеты `events` и `common`;
  как устроены события и состояние игры на каждом тике; как получить tick rate и номер тика;
  какие поля бывают пустыми в битых демках; какие события есть только в новых CS2-демках
  (например, `BulletDamage`). Конспект с короткими примерами кода — в `docs/notes/demoinfocs.md`,
  на него опираются шаги 5–7.
- Утилита `cmd/parsedemo`: путь к `.dem.zst` → потоковая распаковка → demoinfocs →
  JSON-сводка: карта, раунды, игроки (SteamID64, ник, сторона), счёт по раундам,
  K/D/A и урон каждого игрока.
- Защита: лимит размера распаковки, таймаут, `recover` от паники парсера.

Готово, когда:
- на всех демках из `bot/testdata/` счёт и K/D/A совпадают с данными FACEIT
  (сверка через статистику матча в Data API);
- время парсинга и пиковая память записаны в `docs/DECISIONS.md`;
- конспект `docs/notes/demoinfocs.md` написан.

Что сделано (2026-11-03 — 2026-11-05):
- demoinfocs-golang `v6.0.0-rc.1` (стабильной v6 ещё нет, запасной вариант — `v5.2.0`) и `klauspost/compress` v1.20.3.
  Конспекты: `docs/notes/demoinfocs.md`, `docs/notes/zstd.md`.
- `internal/demo` — единственный пакет, который зависит от demoinfocs:
  - zstd распаковывается потоком, окно не больше 32 МиБ, распакованное не больше 1 ГиБ;
  - разбор с таймаутом по ctx и `recover`;
  - результат — `demo.Match`: карта, tick rate, команды со счётом по таймам и овертайму, раунды со счётом,
    игроки (SteamID64, ник, команда, стартовая сторона, K/D/A, HS, урон).
- Как считаем:
  - отсчёт с последнего `MatchStart` — у FACEIT перед разминкой идёт предматчевый раунд;
  - разминка и события после конца матча не считаются;
  - жертва убийства и попадания определяется по pawn: при захвате бота библиотека берёт её по `userid`, то есть контроллёра;
  - боты в сводку не попадают.
- `cmd/parsedemo`: JSON-сводка, время и пиковая память; `-faceit` — сверка со статистикой Data API по SteamID64.
- Сверка `go run ./cmd/parsedemo -faceit testdata` на обеих демках:
  - счёт с таймами и овертаймом, K/D/A, HS и урон совпали у всех 20 игроков;
  - обе демки — матчи kolyx, он найден по SteamID в составах FACEIT;
  - до правила о pawn было расхождение: лишняя смерть у одного игрока и урон −46 и −54 у двух — захват бота.
- Время и память — в DECISIONS: 3,6–6,8 с на демку, пик 60–74 МиБ, две демки параллельно — до 115 МиБ.
  1 ГБ хватает, лимиты юнита не меняли; по согласованию обновлён комментарий о них в `deploy/fragmentor.service`.
- Тесты:
  - правила подсчёта на синтетических событиях, распаковка, ошибки разбора;
  - интеграционные на демках из `bot/testdata/`, без `-short`, ~12 с.
- Сводка помечается `suspicious`, если сыгранные раунды не сходятся со счётом или с подсчётом игры и при других
  предупреждениях; `parsedemo` тогда выходит с кодом 1. Обе демки не подозрительные.
- METRICS.md, «Общие правила» (согласовано 2026-11-05):
  - итоговые K/D/A, HS и урон — по правилам, совпадающим с FACEIT;
  - остальные метрики — тренерские: без смертей от выхода, мира и самоубийств, без ботов под управлением компьютера
    в дуэлях и стрельбе, бот под управлением игрока — сам игрок;
  - случаи, которых не было в двух демках, помечены «Не проверено» — при первом таком матче сверка через `parsedemo -faceit`.
  - На шагах 5–6 в событиях нужны и тело (pawn), и контроллёр — см. конспект demoinfocs.
- Проверено: `gofmt`, `go vet`, `go test ./...`, в том числе с `-race`.

## Шаг 8б. Текст разбора от LLM

Цель: находки превращаются в разбор живого тренера на ru и en.

- Клиент polza.ai по их документации, конспект `docs/notes/polza.md`; таймауты, ретраи, в логах токены
  и стоимость. Тесты — на `httptest`, по правилу CLAUDE.md. Живая проверка — с ключом, который я сам
  положу в `bot/.env` (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`).
- LLM получает только факты из 8а: формулирует, не анализирует. Упражнение выбирает только
  из переданных ID.
- Промпт тренера: тон, структура, длина, запреты (не выдумывать нормы, не советовать без доказательства
  из фактов). Версия промпта хранится вместе с разбором.
- Ответ LLM — JSON: пункты со ссылкой на ID находки и текстом. Сообщение собирает код, разметка
  от модели не приходит.
- Проверка ответа: все числа, зоны карты и номера раундов есть в фактах — у каждого пункта в его находке,
  ID упражнения из списка. При нарушении — повтор, затем шаблон из 8а.
- Кэш по (матч, игрок, язык, версия фактов, версия промпта), ограничение `max_tokens`.
- Оценка: `parsedemo -llm` генерирует разборы для всех демок testdata на обоих языках рядом
  с шаблонными.

Готово, когда:
- проверка ловит выдуманное число, зону и ID упражнения (есть тесты);
- стоимость разбора видна в логах;
- тексты по всем демкам testdata я прочитал и согласен с ними; правки промпта записаны в `docs/DECISIONS.md`.
